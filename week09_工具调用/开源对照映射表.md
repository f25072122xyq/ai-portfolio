# 开源对照：5行流水线映射表（W9加分项）

| 我写的 tool_agent.py | smolagents 框架里对应什么 | 核心差异与思考 |
| :--- | :--- | :--- |
| **TOOLS 字典**：手动将名字映射到函数 | `@tool` 装饰器把带类型注解的函数变成 Tool，交给 `ToolCallingAgent(tools=[...])` | 框架通过装饰器自动提取文档和参数类型，省去了手写字典的繁琐。 |
| **SYS 提示词**：手写长字符串要求输出 JSON | 使用模型原生 tool calling (JSON-like)，提示模板在 `toolcalling_agent.yaml` | 框架的提示词更加系统化，且适配了不同模型的原生工具调用接口。 |
| **parse_calls 函数**：剥围栏、正则兜底抓 JSON | 框架内部解析 `ChatMessageToolCall`，不用自己写正则 | 框架底层处理了各种大模型的畸形输出，开发者无需关心字符串解析。 |
| **TOOLS[name](*args) 执行 + 异常兜底** | 框架按 `Tool.inputs` 校验参数后调用，执行结果进入多步消息 | 框架增加了参数结构的强校验，避免了类型错误或格式错误。 |
| **run() 循环**：手动回喂 + `max_calls` 收口 | `MultiStepAgent` 的多步循环由框架管理步数与停止条件 | 框架自动管理了多轮对话的上下文和最大步数，防止死循环。 |

## 反思总结

在查阅 smolagents 的资料并制作映射表时，我发现我手写的 60 行循环代码虽然能跑，但极其脆弱。比如为了提取 JSON，我必须手写正则表达式去剥离大模型可能带上的 Markdown 围栏，只要模型稍微不听话，我的代码就会报错。

而 smolagents 这样的成熟框架，它用 `@tool` 装饰器和原生的 tool calling 机制把这些脏活累活全包了。框架确实能让我们开发更快，但它也把“模型到底调了什么、怎么校验参数”藏进了一层抽象里。如果只学框架，遇到报错我就会束手无策。先手写，我知道了底层的痛点；再看框架，我才真正体会到它替我省了多少事。
